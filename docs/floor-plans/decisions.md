# 평면도 데이터 결정 기록

새 결정은 위에 추가한다. 날짜, 무엇을, 왜.

## 2026-10-26 · 지도용 평면도 이미지를 무손실 WebP로

- **상황**: 기본 평면도 PNG(약 5MB)와 확대용 조각 PNG 1,317장(약 12MB)이 앱에 그대로 들어가 설치 용량이 20MB 가까이 늘었다.
- **비교** (조각 1,317장 기준, PNG 12.1MB):

  | 방법 | 크기 | 화질 |
  |---|---|---|
  | **무손실 WebP** | **6.9MB (−43%)** | 256색 PNG와 픽셀이 같음 |
  | 손실 WebP q80 / q90 | 15.5MB / 20.5MB | 선 주변이 번지고 오히려 커짐 — 평면도처럼 선·면 위주인 그림엔 손실 압축이 안 맞는다 |
  | PNG 16색 | 8.9MB (−26%) | 선 가장자리가 계단처럼 보임 |
  | PNG 32·64색 | 11.1~11.7MB | 거의 안 줄어듦 |

- **결정**: `renderFloorOverlay.js`가 지금처럼 256색으로 줄인 뒤(upng-js) **무손실 WebP**(`sharp`, effort 4)로 저장한다 → `{층}.webp`, `hires/{층}_{행}_{열}.webp`. 다시 구우면 그 층의 예전 `.png`는 지운다.
- **읽을 수 있는지**: 네이버 지도 라이브러리가 iOS는 `UIImage imageWithData`(iOS 14+ WebP 지원), Android는 Fresco로 이미지를 읽어 둘 다 WebP를 읽는다. Metro도 `.webp`를 기본 에셋으로 다룬다.

## 2026-10-25 · 네이버 지도 평면도 확대 화질: 지금은 고해상도 타일, 벡터 변환은 출시 후

- **상황**: 네이버 지도 위 평면도는 층마다 미리 구운 PNG 한 장(긴 변 약 3000px, `PX_PER_SVG_PX = 1`)이다. 줌 20~21에선 PNG 1px이 화면 2~3px로 늘어나 흐리다. 내부 지도 뷰는 SVG라 멈추면 보이는 영역만 다시 그려(`SharpViewportLayer`) 선명하지만, 네이버 지도는 SVG를 못 그리고 이미지(GroundOverlay)만 얹는다.
- **검토한 방법**

  | | 원리 | 판단 |
  |---|---|---|
  | PNG를 2배 해상도 한 장으로 | 굽는 배율만 올림 | ❌ 층 하나 GPU 메모리 약 140MB(6000px²) — 저사양 기기 위험 |
  | 실시간 렌더 | 카메라가 멈추면 보이는 영역을 기기에서 SVG → PNG(`toDataURL`)로 그려 GroundOverlay로 덮음 | ❌ 회전 도면용 중첩 SVG 지원이 플랫폼마다 불확실, 배경 SVG의 화장실 그림이 화장실 마커와 겹침, 멈출 때마다 PNG 생성 지연 |
  | **② 고해상도 타일** | 스크립트가 고해상도 PNG를 작은 조각으로 미리 굽고, 확대했을 때 화면과 겹치는 조각만 GroundOverlay로 얹음 | ✅ **지금 적용** |
  | **③ 벡터 변환** | 도면 SVG를 네이버 지도 폴리곤·폴리라인으로 바꿔 그림 | ⏸ **출시 후 개선 과제** |

- **② 고해상도 타일 (지금)**
  - `renderFloorOverlay.js`가 기본 PNG와 같은 그림(회전, 라벨·아이콘 제거, 잘라 굽는 층 그대로)을 **1px = 2cm**로 한 번 더 그려 1024px 이하 조각으로 자른다 → `src/assets/floorOverlays/hires/{층}_{행}_{열}.png`. 다 투명한 조각은 버린다. 층마다 도면 축척이 달라(A동은 R동보다 1px이 약 2배 큼) 기본 PNG의 배수가 아니라 실제 길이로 정했다 — 줌 21의 3배 화면 1px이 약 2cm다.
  - `floorOverlayImages.ts`에 층별 `tiles`(조각 이미지 + region)와 `tilesMinZoom`(기본 PNG 1px이 3배 화면 1px보다 커지는 줌 + 0.5)을 같이 쓴다. +0.5는 바로 바꾸면 화면에 걸리는 조각이 너무 많아서.
  - 앱: 화면이 카메라가 멈춘 줌·영역을 `useSettledMapViewport`(NaverMapView `onCameraIdle`)로 기억해 `FloorPlanOverlay`의 `viewport`로 넘긴다. 줌이 `tilesMinZoom` 이상이면 보이는 영역(각 변 25% 여유, `utils/geoRegion.ts`)과 겹치는 조각만 기본 PNG 위(zIndex 2)에 얹는다. 지금 쓰는 곳: 검색 지도, 길 안내.
  - 조각은 작아서 보이는 몇 장만 GPU에 올라간다. iOS·Android 모두 기존과 같은 GroundOverlay라 기기별 위험이 거의 없다.
  - 대가: 조각이 기본 PNG 용량의 약 2배(R·C동) ~ 6배(A동). 시험 3개 층(R_B3·A_1·C_6) 기준 기본 160KB → 조각 410KB.
- **③ 벡터 변환 (출시 후)** — 선명도는 줌과 상관없이 완벽하고, PNG(약 5MB)를 없앨 수 있어 용량도 준다. 출시 전에 하지 않은 이유는 작업량과 위험:
  - 2026-10-25 기준 배경 SVG 154개 분석: 층당 도형 중앙값 94개(최대 258), 사각형 14,654 · 곡선 path 547 · transform 7,293 · **mask 243**(Figma 안쪽 선 → 도형을 직접 깎아야 함) · **evenodd 670**(구멍 난 폴리곤) · **stroke 11,163**.
  - 네이버 폴리라인 두께는 화면 px 고정이라 확대해도 벽이 안 두꺼워진다 → 선을 전부 두께 있는 폴리곤으로 바꿔야 한다(오프셋 라이브러리).
  - 예상 5~7일: 변환 스크립트(path·곡선 근사·transform·구멍·mask·선→면) 2~3일, 앱 렌더러(겹침 순서·하이라이트·라벨) 0.5~1일, 154층 검증(기존 PNG와 자동 비교) 1~2일, iOS·Android 성능 확인 0.5~1일. 층별 Figma 예외에 따라 늘어날 수 있다.
  - 적용하면 ②의 타일과 기본 PNG를 지운다.

## 2026-10-23 · H동 1층은 G동 4층 도면의 위쪽 날개로 연결, H_1 파일 삭제

- **상황**: `H_1.svg`는 `G_4.svg`와 내용이 같은 사본이었다(위쪽 날개 101~106 = H동 1층, 아래 4xx = G동 4층). 지도 기준점도 없어 지도에 안 깔렸고, H동 1층에서 410을 누르면 "H동 410호"로 나왔다.
- **결정**: H_1 파일을 지우고 `hostedFloors.json`에 `"H_1": { "floorId": "G_4", "maxY": 335 }`(날개 아래 벽 y≈330). 아래 J동과 같은 방식.
- **주의**: Figma에서 다시 내보낼 때 H_1을 `FLOOR_MAPS`에 다시 넣지 않는다.

## 2026-10-23 · 도면 번호의 자기 동 글자는 뗀다

- H동 3~6층 Hitbox는 "H317"처럼 동 글자가 붙어 있는데 서버는 "H동 317호"다. `getRoomOwner`가 `^{동}\d`면 뗀다. 지하 표시 B(G동 B110, R동 B212)는 동 글자가 아니라 그대로 둔다.

## 2026-10-22 · 배경 SVG에서 글자로 된 방 이름도 지운다

- **상황**: `stripLabelPaths.js`가 숫자 번호만 지워서 "계단 세미나실", "Hall" 같은 이름이 배경과 앱 라벨로 두 번 그려졌다.
- **결정**: `processFloor.js`가 방 JSON을 먼저 만들고 `stripLabelPaths.js --rooms=<json>`으로 방 이름과 같은 path도 지운다(지도용 PNG는 원래 이 기준으로 지우고 있었다).

## 2026-10-22 · J동은 L동 도면 아래쪽, 지도에선 화면마다 다르게

- **상황**: J동(제3공학관)은 자기 도면이 없고 L동(와우관) 4~8층 도면 아래쪽에 J로 시작하는 호실로 들어 있다. 서버는 "J동 101호"(J동 1층)처럼 J동 기준 층을 준다.
- **결정**:
  - `hostedFloors.json`: `J_B2~J_3` → `L_4~L_8`, J동 부분은 `minY: 740`(계단 3개 연결 통로 아래 복도 + 호실 줄).
  - 방 소속은 위치로 정한다: 도면에서 그 동 부분 안에 있는 방은 그 동(`getRoomOwner`). 카드·즐겨찾기·길찾기가 서버 이름과 맞는다.
  - 지도에 깔 도면: **검색**은 그 동 부분만 잘라 구운 PNG(`J_1.png`), **길 안내**는 L동 전체 도면(L동 계단·통로로 이어지는 길이 보여야 해서), **건물 내부 보기**도 L동 전체.
- **도면은 두 가지뿐**: 잘라 구운 PNG(검색용)와 원래 L동 도면. 길 안내용 도면을 따로 만들지 않는다.

## 기준점·PNG

- 지도 위치는 서버 평면도 꼭짓점 두 개 + Figma 기준점 두 개로 닮음 변환(이동·회전·균일 확대) → 네 모서리(`floorPlanAnchors.json`). 손으로 찍은 기준점은 쓰지 않는다(2026-10-21부터).
- 네이버 GroundOverlay는 SVG를 못 받고 남북 정렬 사각형에만 펼치므로, 빌드 때 도면을 돌려 투명 이미지(무손실 WebP, 2026-10-26부터)로 굽고 region을 같이 저장한다. 번호·아이콘은 이미지에서 빼고 앱이 마커로 똑바로 그린다.
